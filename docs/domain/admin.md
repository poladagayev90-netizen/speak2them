# Admin accounts, admin nav + Activity, admin panel

Moved out of CLAUDE.md on 2026-10-15 so it is read only when a task touches this area. Facts are kept as written; keep this file current when the code changes.

- **Admin accounts** (2026-10-07): the admin uid OR a VERIFIED e-mail in `ADMIN_EMAILS` (poladagayev90 / agayevpoli7) — `isAdmin()` in rules, `isAdminToken(decoded)` in functions, `isAdminUser(user)` in `src/constants.js`; keep the three lists in step. `ADMIN_UID` stays the admin IDENTITY (admin pushes, the admin's own students' `teacherId`, unlimited practice) — only permission checks take the e-mail.
- **Admin nav + Activity** (2026-10-07): an admin gets their own bottom nav **Today · Activity · Week · Students · Admin** (`BottomNav.jsx`; Partners and Lab are icons in Today's header). The tabs come in groups (`src/utils/adminNav.js`, `?tab=` is the state): activity · week (Matching, Week) · admin (Students, Applicants, Sessions, Attendance, Intros). Activity (`AdminActivity.jsx`) = who is in the app / in a call now (admin may list `calls`), every finished call from `callLog/{callId}_{start}` (written once by `reconcileCallStats` via `functions/callLog.js`, admin-read; `adminCallLogBackfill` fills 30 days from `practiceSessions`), and app use by hour from `presenceDays/{uid}_{bakuDate}` (`src/utils/presenceLog.js`: the heartbeat writes `arrayUnion(hour)` only when the Baku hour changes; owner-written, admin lists, a teacher GETs their students' days by id). Teachers: the dashboard (`TeacherUnlock.jsx`, 2026-11-07, Polad's 23 Oct list item 7 «qarışıqlıq itsin») is two tabs since 2026-11-10, `?tab=` keeps the choice: **Today** (a compact **Class summary** card — active this week, class average, students with reports, the 3 most repeated error themes as chips — then Add a student for the admin, This week, My students, scheduled calls + «Set up a call») · **Invite & profile** (`?tab=setup`, tutor profile, invite code with a pencil to change it, Copy link, WhatsApp, pick from users). The Class tab became the summary card (an old `?tab=class` lands on Today); the e-mail «Invite a student directly» form and the Video library card are gone from the panel (`/teacher/videos` still opens by link). **No «create a code» step**: on first open the code is made from the teacher's first name + 4 digits (`src/utils/teacherCode.js`, tested: Azerbaijani/Cyrillic letters → A–Z, max 8 + 4 = 12, e.g. POLAD2005); `code-taken` → another number, up to 4 tries; any other failure shows the old manual form. Changing the code later calls the same `createInviteCode` — the OLD code keeps working, so sent links do not die. The old manual-call blocks stay until Polad decides they can go. My students are sorted by **most recent practice** (`latestPracticeMs`), never-practised = newest joiner first (was online-first until 2026-11-10); the dot and «Online / Seen 2 h ago» still show presence. A student's page is tabs **Progress** (the learner's own Lab read-only — `Progress learnerUid`) · Lessons · Activity (14 days of hours), with **Download PDF** at the top: it switches to Progress and opens the browser's print dialog (`body.ts-printing` print CSS in App.css hides header, nav, tabs and buttons; the theme is forced light while printing; a print-only head carries the name and date). The Android app WebView has no print dialog, so there it says to open the page on a computer. «Did you apply it?» cards: the status is its own line under the title and the grid is `auto-fit minmax(240px)` → 3, 2 + 1 or 1 column (a fixed 3 columns broke long titles letter by letter).
- **Admin panel** (`src/pages/Admin.js` + `Admin.css`): compact sticky header + tabs Students (with the Packages switch and a per-learner package menu) · Applicants · **Matching** (`AdminMatching.jsx`, pure helpers `src/utils/matching.js`: the **people console** beside the week's real pairs, open proposals + bookings; "Change" swaps one side by withdrawing the offer / `cancelSlotMatch` and proposing the new pair; wide layout on a computer — see **Matching** below) · Week (`?tab=plan` still works) · Sessions · Attendance · Intros (the old Cohorts tab is hidden since 2026-10-03; `AdminCohorts.jsx` is kept). On a phone nothing in a tab may be wider than the screen: rows wrap (`.aa-roster-row` puts Auto/Always/Never under the name) and every block in `.adm-body` has `min-width: 0` — a non-shrinking flex row once made the whole tab, week chips included, run off the edge. Live admin lists must not reorder under the admin's finger — use `stableOrder` (`src/utils/stableOrder.js`): a row keeps the place it got when it appeared until the filters change. Panels that grow with a selection go in a bar pinned to the bottom (`aa-sticky-bar`), never above the list.
- **Matching — people console** (2026-10-18; `PeoplePanel` in `AdminMatching.jsx`, helpers `freeGrid` / `weekRanges` / `attentionOf` in `src/utils/matching.js`, tested). One row per person: name, level, new, planned of wants, the week's verdict (autopilot: `weekRoster/{monday}.autoIn` / `autoWhy`; manual: in the list or not), paid / account health / reliability tags, a WhatsApp button (`whatsAppLink(onboarding.whatsapp)`) and a chevron that opens the Applicants answers (`ApplicantDetail`, exported from `AdminApplicants.jsx`). **Free-time grid** = 7 rows × hourly Baku starts 07–23 (`SLOT_START_HOURS`), a cell lit when ≥ 30 free minutes follow the start (`startFitMin`, the same rule as the pickers and the planner — the old 7×8 grid of 2-hour blocks lit at ≥ 60 min showed a 19–22 learner at 18 and 20). It draws the week the planner sees (`weekRanges` mirrors `autoRoster.weekAvailability` / `weekMaybe`): that week's picked hours (`onboarding.weeks.{monday}.hours`, dark), else usual times on the picked days, else the usual times (light), always minus «Never»; usual time left out that week = faintest; «Maybe» = an outline; a practice of theirs = solid at its real start hour. **Needs attention** box at the top: counts that act as filters (over everyone, list or not) — in this week but 0 planned; new (no call, joined ≤ 14 days) without a first practice; paid but snoozed / asleep / sleeping / ghost; reliability `limited`; no WhatsApp. Rows keep `stableOrder`.
- **Plan selected** (2026-10-18): tick two → one proposal for a time (as before) or «Let the planner choose»; tick 3–40 → the pinned bottom bar. «Plan these N» = `adminWeekPlan` `planSelected {uids, weekKey}`: `loadPlannerInputs(…, { only: uids, dryRun: true })` — the admin's pick stands in for the list / autopilot verdict / account health / 21-day activity gates (like «Always»), billing, pause, targets and every pairing rule still apply, nothing is written — then `buildWeekPlan` over the days left (≥ 3 h ahead). It returns the pairs, `unmet` and `skipped` (not planned at all). «Book these» = `bookSelected {uids, pairs}`: each pair (both sides among `uids`, a valid start that week, ≥ 3 h ahead, ≤ 9 days) goes through `directBookTx` with `adminPick` (no week answer needed; paused refuses) → `bookPairTx` (pairVerdict, one a day, no overlap, practices left), push `plan_booked`, `planStatus` booked. Only `{booked, refused}` comes back — never which rule refused. Same rate limit as the other `adminWeekPlan` actions (200/day).
