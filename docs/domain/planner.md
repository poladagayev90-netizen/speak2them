Moved out of CLAUDE.md on 2026-10-15 so it is read only when a task touches this area. Facts are kept as written; keep this file current when the code changes.

- **Weekly plan** (Phase 3; `functions/weeklyPlanner.js` pure + tested, `functions/availability.js` = server copy of `src/utils/timezone.js` — keep them in step): every Sunday 12:00 Baku `practiceSlotTick` drafts `weeklyPlans/{monday}` (admin-only) from onboarding availability (≥ 30 free minutes from a block's start) + `weeklyTarget`, under pairVerdict's hard rules, one practice a day, no repeat pair a week, fairness first (1/n weighting). Admin → Week plan reviews it (remove / move / hold / send, `adminWeekPlan`). Sending turns each pair into an ordinary `matchOffers` doc (`source: weekly_plan`, `planWeek`, `respondBy`), one `week_plan` push per person, and an honest `planStatus/{uid}` (owner-read). `appConfig/planner` switches — **`autoSend` (Sun 20:00) and `refill` (hourly 08–21, mid-week) are ON in production since 2026-10-06** (Polad: calls must get set up even when the admin is away; an auto-send pushes the admin `admin_plan_sent`). Plan offers give **48 h** to answer (`respondBy`), refill offers 6 h; whoever has not answered gets ONE `match_offer_reminder` halfway / at 12 h (`functions/offerReminders.js`, claimed in `reminded.{uid}`). A 20-learner emulator run of the whole week (`scratchpad/sim20.js`, `exports._sim` exists only under `FUNCTIONS_EMULATOR`) booked 80% of what eligible learners asked for. `requireCharter` limits planning to learners who accepted the charter.
- **Autopilot** (2026-10-06, `functions/autoRoster.js` pure + tested, client mirror `src/utils/myWeek.js`): `appConfig/planner.rosterMode` `manual` (default — the admin's list below) or `auto` (Admin → Week → «Who practises» switch). In auto the planner (plan + refill) looks at EVERYONE set up and `eligible()` decides. **Default «in», opt-out (Polad 2026-10-18)**: seen in the last **7 days** AND practices left = planned on their usual times (`usual_times`) unless they changed the week — `onboarding.weeks.{monday} = {days, hours, at}` (other hours, `said_in`) / `{skip}` (week off), owner-written, it grants nothing — or paused. The weekly «are you in?» question had left out free learners who just forgot to answer. In reasons `said_in / package / regular / new / usual_times / included`; out reasons `asleep / skipped / snoozed` (2 plan/refill proposals in a row left unanswered, until they answer or pick hours) `/ no_practices_left / paused / not_set_up / excluded` (`not_confirmed` no longer happens; old `autoWhy` docs may still carry it). Account health and reliability limits still filter after `eligible()`; `directBook` still books only two who both picked hours (`committed`), a `usual_times` learner gets a two-yes offer. The picked days narrow that week's free times and set the number (one a day). The verdicts are written to `weekRoster/{monday}` (`autoIn`, `autoWhy`, `autoSummary`) — the slot board and old-APK random search read them; the admin only overrides per person (Always = `include`, Never = `exclude`). Auto also: Saturday 12:00 `week_checkin` push / Sunday 10:00 `week_checkin_reminder` (package learners `plan_tonight`) — since 2026-10-18 they TELL, not ask: «next week on your usual times — other hours or a week off in the Plan tab», the 20:00 send rebuilds the noon draft if the admin did not edit it, and Sunday writes `appConfig/popularTimes` (learners free per Baku block, ≥3 only, no names) — Onboarding dots the 6 busiest blocks «Popular», a `no_match` card offers «Add Tue 20:00» in one tap. Learner side: Plan tab «Your week» (`WeekCalendar`, 2026-10-07: this/next week as an hour grid — the onboarding grid, shared `components/plan/TimeGrid.jsx` — with the day buttons as column heads; it starts from ALL the usual times (no answer = «Your usual times · N practices», N = `weeklyTarget`; buttons «Take the week off» = `skip`) and a tap changes ONLY that week, `weeks.{monday}.hours = {wd: [h]}` + `days`; the server turns `hours` into that week's ranges, `autoRoster.weekAvailability`; max 4, one a day; «Use these times every week» also rewrites `availability`; Plan shows Today's card only for setup / paused / no_match / a limit / no practices left; in auto, someone in for this week reads «Looking for partners · Wed, Thu», not «Sunday»; the week's goal = `weekGoal`); Today's `checkin` card (2026-10-18: weekend only, about next week, when there is no answer and the server's `planStatus.auto` does not count them out — «Next week on your usual times», «Change hours» → Plan, «Take the week off» = `skip`; on a weekday someone with no answer is simply «Looking for partners»). Client mirror: `myWeek.autoIn` = the server verdict for that week when there is one, else true. Real-life simulation: `scratchpad/simlife.js` (RUN=manual|away|auto, personas, 6 weeks, real `practiceSlotTick`).
- **Account health + direct booking** (2026-10-14, AI-planner plan Mərhələ 1; `functions/accountHealth.js` pure + tested): six weeks of prod offers gave 3 confirmed of 42, a yes waited a median 24 h for a no, and accounts with no call ever kept getting offers. `loadPlannerInputs` now classifies every learner (both roster modes) `active / new / sleeping / ghost / suspicious` and plans only active + new (auto's «Always» overrides); verdicts go to admin-only `accountHealth/{uid}` (`cls`, `why`) — the admin may set only `flag: 'suspicious'` (Admin → Week rows, flag button). `appConfig/planner.directBook` (default OFF): two learners who both said «in» for the week (`onboarding.weeks.{monday}`) are BOOKED straight away (`directBookTx` → `bookPairTx`, push `plan_booked`, `planStatus.state: 'booked'`) in the Sunday send and the refill (refill notice 3 h instead of 10 h); everyone else still gets a two-yes offer. First yes on an offer: the other side's `respondBy` shrinks to ≤ 6 h (never later than before) and they get `match_offer_partner_yes` instead of the halfway reminder. A cancelled / partner-no-show booking, an expired or declined offer that had a yes → `plannerState/refill.wantedAt` (server-only), and the next minute tick runs the refill (within 08–21, refill ON) instead of waiting for the hour; whoever had said yes counts as let down (refill priority).
- **Newcomer's first practice** (2026-10-15, `functions/newcomers.js` pure + tested): the prod funnel had 1 of 14 newcomers reach a practice — 8 never came back after signing up, 9 had no push, the refill paired them with gone accounts. Now (1) finishing the wizard = «in» for 3 days (`committedFor`: their own week answer wins; used by `loadPlannerInputs` and `directBookTx`), and `notifyAdminOnboarding` calls `requestRefill`, so directBook can book them before they close the app; (2) `pairAllowed` refuses a newcomer + someone with `newcomerOk === false` — an older learner must have a push token and a practice (`users.lastPracticeAt`) or a yes in the last 14 days; another newcomer must have been seen in the last 48 h (missing field = not judged); (3) the refill books a newcomer who is in, fresh (48 h) and has nothing this week with a HOST from `appConfig/planner.newcomerHosts` (≤5; a uid = their own onboarding grid, or `{uid, hours: {weekday: [Baku hours]}}` — the admin has no grid) at the earliest shared start within 72 h (`hostPairs`, never a minor with an adult, never the host's own student — `users.teacherId`, Polad 2026-10-15; one per host a day, so the host gets at most as many as their free hours). The booking is `source: 'team_intro'` with marker `{host, team: true}`: it never counts against the learner's free practices / package (`packages.bookingVerdict`) nor in reliability (attendance `team`). No hosts configured = nothing changes there. Prod (Polad 2026-10-15): the admin only, hours in Baku from his calendar — weekdays 10:00, Thursday 10–11, weekends more. The admin is never planned as an ordinary learner, so he meets only newcomers this way. (4) Onboarding has a `notify` step after `phone` (`src/utils/pushOptIn.js`, shared with `NotificationPrompt`), passed over where push is on, blocked or unsupported. - **AI planning analyst** (2026-10-14, Mərhələ 2; `functions/agent/` pure + tested: `packet.js`, `validate.js`, `gemini.js`, `prompt.js`): Gemini (`appConfig/agent.model`, default `gemini-3.8-flash`, secret `GEMINI_API_KEY`, native fetch, JSON `responseSchema`) runs every morning ≥07:00 Baku for this week and Sunday ≥11:00 for next week (`runAgent`, claimed in `slotRuns`; Admin → Agent «Run now» = `adminAgent`). It sees ONLY aliases (L1…), CEFR level and practice numbers (attendance 28 d, partnerFeedback tags 60 d, declines, health, reliability) about the pairs `weeklyPlanner.candidatePairs` allows (top 8 per person) — never names, uids, age, country, WhatsApp, e-mail, time zone, transcripts or chat. It returns pair scores (clamped ±2 = one favourite star → `aiAffinity/{monday}` → `buildWeekPlan({ aiBonus })`), ≤5 «look at this account» suggestions (the admin flags; the AI never does) and a short Azerbaijani report (aliases → names server-side) in `agentReports/{date}_{monday}`. `appConfig/agent`: missing / `enabled:false` = nothing runs; `mode: shadow` = the plan stays deterministic, both versions in `agentRuns/{monday}`; `act` = plan + refill use the scores unless that gives fewer people a practice. `monthlyBudgetUsd` (default 5) vs `agentUsage/{YYYY-MM}.usd` stops it (push `admin_agent_budget`). Any failure leaves the planner as it was. All four collections admin-read, server-write.
- **Weekly roster** (2026-10-02, `functions/weekRoster.js`, = `rosterMode: manual`): only the people the admin ticks in Admin → Week → "Who practises" (`weekRoster/{monday}.uids`, admin-only rules) are planned (`loadPlannerInputs` — plan and refill), may join a practice block (`joinSlotTx` → 403 `not-in-roster`) or be matched at random (`canPair` without `direct`). **No list saved for a week → the most recent list of the last four weeks carries over** (`rosterOf`; the Sunday draft writes it down with `carriedFrom`, and Week/Matching say so); only when there has never been a list is it nobody — then the draft stores `noRoster` and pushes the admin `admin_roster_missing`. Dead accounts drop out through the planner's 21-day activity filter, not the list. Direct calls, admin proposals and teacher pairs are not gated.
- **Reliability** (Phase 5, `functions/reliability.js` pure + tested): over 28 days, only CONFIRMED practices — `no_show` +1, `late_cancel` +0.5, a booked `attended` −0.5; `partner_no_show`, `unmatched`, in-time cancels, unanswered proposals and direct calls never count. `watch` ≥ 1 point (admin only); `limited` ≥ 3 points or two no-shows in a row → the weekly plan gives ONE practice a week and never pairs them with a newcomer (`callCount` 0); two booked practices attended in a row lift it. `refreshReliability` runs at block close and on a late cancel and writes admin-only `reliability/{uid}`; the learner sees only `planStatus.limit` (reason + way back, never the points) on Today/Plan. Admin → Attendance shows the level and a Reset (`adminWeekPlan` `resetReliability`). At +10 min the one who came gets `partner_late` (it says "we're looking for another time" only when `refill` is on); the refill writes `replacement_not_found` when it finds nothing.
- **Favourite partners** (`users/{uid}/favorites/{peerId}`, owner-only, `src/utils/favorites.js`): a star on Partners or "I'd like to practise with them again" after a call. The planner adds +2 per star (mutual = +4) and skips the recent-partner penalty for a starred pair; it is a preference, never a promise, and the starred person is never told.
